# TypeScript Bindings: Multi-Environment & External ABI Support

Generated by `glassbox generate-bindings`.

---

## Runtime Targets & Environment Matrix

The binding generator supports three runtime targets, selected with `--runtime`:

| Target | Flag | Description |
|--------|------|-------------|
| **Node.js** | `--runtime node` (default) | Uses `child_process.spawn` for the Glassbox simulator. Lets the Stellar SDK use its built-in Node transport. |
| **Browser** | `--runtime browser` | Uses the global `fetch` API. No `child_process`, `fs`, or other Node-only imports. Safe to bundle with webpack/Vite/esbuild. |
| **Universal** | `--runtime universal` | Emits runtime environment-detection code. Works in Node.js, browser, and Electron renderer processes without separate builds. |

### Capability & Compatibility Matrix

| Feature / Capability | Node.js (`--runtime node`) | Browser (`--runtime browser`) | Universal (`--runtime universal`) |
| :--- | :--- | :--- | :--- |
| **Default Target** | Yes (when `--runtime` omitted) | No (explicit opt-in) | No (explicit opt-in) |
| **Simulation Transport** | Local subprocess (`child_process.spawn`) | HTTP API (`globalThis.fetch` to daemon/RPC) | Hybrid: subprocess in Node, HTTP in Browser |
| **Node.js Built-in Imports** | `child_process` statically imported | **None** (`child_process`/`fs` omitted/stubbed) | Dynamic/lazy `require('child_process')` in Node |
| **Stellar SDK Transport** | Node.js HTTP/HTTPS transport | Browser `window.fetch` / `globalThis.fetch` | Auto-selected (`_pickFetch`) |
| **Bundler Compatibility** | Node runtimes only (Webpack/Vite error if unpolyfilled) | Safe for Vite, Webpack, esbuild, Rollup | Safe for bundlers with conditional exports |
| **`package.json` Fields** | Standard entrypoints | Includes `"browser"` field excluding Node modules | Includes conditional `"exports"` map |
| **Custom Provider Support** | Supported (`SorobanProvider`) | Supported (`SorobanProvider`) | Supported (`SorobanProvider`) |
| **Min Node Version** | Node 16+ | N/A (runs in web browsers) | Node 18+ (or Node <18 with `node-fetch`) / Modern Browsers |

### Environment Examples

#### 1. Node.js Environment Example (Default)

Designed for backend services, CLI utilities, and server-side automation where the local `glassbox-sim` or `glassbox` CLI binary is installed.

```bash
# Generate bindings for Node.js
glassbox generate-bindings contract.wasm --runtime node --output ./src/bindings
```

```typescript
import { MyContractClient } from './src/bindings';
import { ErstSimulator } from './src/bindings/Glassbox-integration';
import * as StellarSdk from '@stellar/stellar-sdk';

const sourceKeypair = StellarSdk.Keypair.fromSecret(process.env.STELLAR_SECRET_KEY!);

const client = new MyContractClient({
  contractId: 'CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQAHHAGCN4B2',
  network: 'testnet',
  enableSimulation: true,
});

// Execute transaction simulation locally via child process
const simResult = await client.transfer(
  sourceKeypair,
  'GDQP2KPQGKIHYJGXNUIYOMHARUARCA7DJT5FO2FFOOKY3B2WSQHG4W37',
  'GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5',
  BigInt(5_000_000),
  { simulate: true },
);

console.log('Simulation status:', simResult.simulation?.status);
```

#### 2. Browser Environment Example (Vite / Webpack / Web App)

Designed for single-page applications (React, Vue, Svelte) and browser extensions. Eliminates `child_process` and `fs` imports so bundlers do not require polyfills.

```bash
# Generate bindings for web browser
glassbox generate-bindings contract.wasm --runtime browser --output ./src/bindings
```

The generated `package.json` excludes Node-only modules from modern bundlers:

```json
{
  "browser": {
    "child_process": false,
    "fs": false,
    "path": false
  }
}
```

Frontend application usage with HTTP simulation:

```typescript
import { MyContractClient } from './src/bindings';
import { ErstSimulator } from './src/bindings/Glassbox-integration';

// In browser environments, ErstSimulator communicates over HTTP with a remote or local Glassbox daemon/RPC
const sim = new ErstSimulator({
  network: 'testnet',
  rpcUrl: 'https://soroban-testnet.stellar.org',
  // Inject custom fetch with authorization or CORS headers:
  fetch: (url, init) => {
    return window.fetch(url, {
      ...init,
      headers: {
        ...init?.headers,
        'X-Client-App': 'MyDApp/1.0',
      },
    });
  },
});

const client = new MyContractClient({
  contractId: 'CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQAHHAGCN4B2',
  network: 'testnet',
});
```

#### 3. Universal Environment Example (Isomorphic Node + Browser + Electron)

Designed for shared libraries, SSR frameworks (Next.js, Nuxt), and Electron applications where the same package is consumed by both Node.js main processes and browser renderers.

```bash
# Generate universal isomorphic bindings
glassbox generate-bindings contract.wasm --runtime universal --output ./src/bindings
```

The generated code detects the runtime environment dynamically at startup:

```typescript
import { MyContractClient } from './src/bindings';

const client = new MyContractClient({
  contractId: 'CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQAHHAGCN4B2',
  network: 'testnet',
});

// The client automatically routes fetch calls:
// - In Node 18+ or Electron main: uses globalThis.fetch
// - In Node < 18: falls back to require('node-fetch')
// - In Browser / Electron renderer: uses window.fetch
```

### Failure Paths & Troubleshooting

| Failure Scenario | Observed Error | Root Cause | Remediation |
| :--- | :--- | :--- | :--- |
| **Node Target in Browser Bundler** | `Module not found: Can't resolve 'child_process'` (Webpack / Vite) | Default `--runtime node` statically imports `child_process`. Browsers do not provide POSIX process primitives. | Regenerate bindings with `--runtime browser` or `--runtime universal`. |
| **Browser Simulation Without Endpoint** | `TypeError: Failed to fetch` or `NetworkError when attempting to fetch resource` | Browser target cannot spawn binaries; it queries the simulator via HTTP. | Start the local simulation daemon via `glassbox daemon` or supply a valid `rpcUrl` in `ErstConfig`. |
| **Node < 18 on Universal Target** | `Error: Cannot find module 'node-fetch'` | Universal target on older Node.js lacks native `globalThis.fetch` and requires the fallback package. | Install `node-fetch` (`npm install node-fetch@2`) or upgrade the Node runtime to version 18 or newer. |
| **Missing Contract Spec in WASM** | `contract spec not found in WASM file` | The WASM binary was compiled without contract specification metadata (`contractspecv0` section). | Rebuild the contract with Soroban CLI (`soroban contract build`) to retain the spec section. |

## Custom Soroban RPC Provider

All runtime targets support injecting a custom RPC provider via the `provider`
field in `ClientConfig`. This lets you:

- Point at a private or local RPC node.
- Supply a custom network passphrase (e.g. for private networks).
- Wrap `fetch` to add authentication headers, logging, or retry logic.

```typescript
import { MyContractClient, SorobanProvider } from './src/bindings';

const myProvider: SorobanProvider = {
  rpcUrl: 'https://my-private-rpc.example.com',
  networkPassphrase: 'My Private Network ; January 2026',
  fetch: async (url, init) => {
    const resp = await fetch(url, {
      ...init,
      headers: {
        ...init?.headers,
        Authorization: `Bearer ${process.env.RPC_TOKEN}`,
      },
    });
    return resp;
  },
};

const client = new MyContractClient({
  contractId: 'CDLZFC3...',
  network: 'mainnet',   // used for network passphrase fallback only
  provider: myProvider, // overrides rpcUrl and networkPassphrase
});
```

When `provider` is set:
- `provider.rpcUrl` takes precedence over `rpcUrl` and the built-in network defaults.
- `provider.networkPassphrase` (if set) overrides the SDK's built-in passphrase for the network.
- `provider.fetch` (if set) is passed to the Stellar SDK's `SorobanRpc.Server`.

## External ABI / Spec Files

By default, `generate-bindings` extracts the contract spec from the WASM binary's
`contractspecv0` custom section. You can skip WASM entirely by supplying an
external ABI file with `--spec-file`.

### Supported Formats

| Format | Flag | Description |
|--------|------|-------------|
| **JSON** | `--spec-format json` | Glassbox canonical JSON ABI (produced by `glassbox abi --json`). |
| **XDR** | `--spec-format xdr` | Raw XDR-encoded `ScSpecEntry` bytes (same binary format as the WASM section). |
| *(auto)* | *(omit flag)* | Auto-detected: files starting with `{` are treated as JSON, everything else as XDR. |

### Generating a JSON ABI from a contract

```bash
# Export the ABI from a deployed contract:
glassbox abi --contract-id CDLZFC3... --network testnet --json > contract-abi.json

# Generate bindings from the exported ABI:
glassbox generate-bindings \
  --spec-file contract-abi.json \
  --package my-contract \
  --output ./src/bindings
```

### Generating bindings from an XDR spec file

```bash
# Extract the raw spec section from a WASM file:
glassbox abi --wasm contract.wasm --xdr > contract.xdr

# Generate bindings from the XDR spec:
glassbox generate-bindings \
  --spec-file contract.xdr \
  --spec-format xdr \
  --package my-contract \
  --output ./src/bindings
```

### JSON ABI format

The JSON format matches the output of `glassbox abi --json`:

```json

        { "name": "amount", "type": "U128"    }
      ],
      "outputs": ["Void"]
```

## CLI Reference

```
glassbox generate-bindings [wasm-file] [flags]

Spec sources (mutually exclusive):
  <wasm-file>              Extract spec from a compiled WASM binary
  --spec-file <path>       Load spec from a JSON or XDR ABI file

Flags:
  -o, --output <dir>       Output directory (default: current directory)
  -p, --package <name>     Package name (default: input filename without extension)
      --contract-id <id>   Contract ID embedded in generated README
  -n, --network <net>      Stellar network: testnet (default), mainnet, futurenet
      --runtime <target>   Runtime target: node (default), browser, universal
      --spec-file <path>   External ABI/spec file (JSON or XDR)
      --spec-format <fmt>  Spec file format: json, xdr (auto-detected when omitted)
      --debug-metadata     Emit ABI metadata objects and withDebugMetadata() wrappers
      --wasm-source <path> Source path hint embedded in debug metadata
```

## Architecture Decision Records

The following ADRs govern the design decisions behind multi-environment bindings:

- [ADR-003: Trust Boundaries and Component Trust Levels](adr/003-trust-boundaries.md) — classifies browser-targeted bindings as Tier 5 (restricted, no subprocess access) and documents the controls — `child_process`/`fs`/`path` exclusion, fetch-API-only simulation — that apply in the browser runtime.
- [ADR-004: Data Classification and Cross-Boundary Data Flows](adr/004-data-classification.md) — documents Boundary G (TypeScript Bindings → RPC) and confirms that no CLI host process is involved in browser-based simulation requests.
